# Stage 2 implementation notes

Stage 2 of [the per-member keys plan](ki01-per-member-keys.md) puts identities into kinship-core. It is split in three: Stage 2a adds the identity configuration, mode `sign` for statements about membership, certificate distribution, per-recipient wire versions and the new counters; Stage 2b adds the Ack and Nack bindings, the probe challenge and signed user messages and broadcasts; both are described here, and implemented. Stage 2c runs the 1,000-seed sweeps in `sign`, the signed tuning comparison and remeasures the costs; it fixes what the sweeps found and caps announcements ([results](results/signed.md)). Nothing here changes a node in mode `off`, the default: it sends the bytes 0.4 sends and the pinned SWIM trace is unchanged. KI-01 stays Accepted, and the feature stays opt-in and planned for a release after 1.0.

## Design

Five questions had to be settled before the code. Each answer keeps version 1 accusation semantics in both modes: a third party's Dead still kills at once, in `sign` as in `off`, until Stage 3.

### 1. Where signatures and certificates live

- **The member table** keeps, beside each member, the proof of the Alive it holds: the incarnation that Alive was signed at, its certificate id and its signature. The rest of the signed bytes (name, address, metadata, version range and epoch) are the member's own fields, which only an Alive replaces, and every path that replaces them sets the proof again or clears it. A member suspected at a higher incarnation keeps the proof of its last Alive, which is what a version 2 push-pull record carries as its original Alive (Stage 1, Push-pull). A Left keeps the member's signed Left beside it (`left` incarnation, `at`, certificate id, signature). A member without a proof for its current Alive is unsigned; `unsigned_members` counts the live ones.
- **Certificates** are held one per member, in a map by name, as the parsed key and validity with the exact bytes they arrived in. A member's certificate is the one its applied Alive was signed under, so it follows the member through a restart with a new key; choosing between two valid certificates by `not_before` is renewal, which is Stage 4. A certificate goes when its member's tombstone is reaped. This node's own certificate is held the same way.
- **The gossip queue** keeps the proof with each rumour: the Alive's certificate id and signature, or an accusation's `at`, certificate id and signature, and for an Alive that is new to the node gossiping it, the certificate's bytes, so it goes ahead of the Alive in every packet that carries it. Each entry knows its length in both grammars.
- Relays and push-pull rebuild the signed messages from these fields. The version 2 encoding has one encoding per value, so the rebuilt bytes are the bytes the author signed, and a relay forwards the signature unchanged.

### 2. Unsigned statements in `sign`

The version 2 grammar has no unsigned Alive, Suspect, Dead or push-pull record, and a signing node holds unsigned ones whenever its cluster has a 0.4 or `off` node: their own Alives, and whatever they relayed, since a 0.4 node drops what it does not know.

- **Envelope selects grammar.** A version 2 packet holds version 2 messages only, all of them signed membership statements, certificates or push-pull; a version 1 packet holds the version 1 grammar, exactly as 0.4 writes it. A signing node never writes a version 2 body into a version 1 envelope, so the upgrade envelope of Stage 1 is not used on the wire.
- **Datagrams to a member that speaks version 2** go out as up to two packets: a version 1 packet with the probe messages (Ping, PingReq, Ack, Nack, which stay version 1 until Stage 2b), the unsigned rumours and the user broadcasts, and a version 2 packet with the signed rumours, each new Alive behind its certificate. Each packet takes its rumours in queue order from the room it has; a rumour goes once per datagram pair and counts one transmission. A member that speaks version 1 only gets the one version 1 packet, every rumour in it in its version 1 form, as `off` sends it.
- **Push-pull with such a member** is a version 2 exchange (A): the signed records, the sender's own certificate, and the ids of the certificates it holds; the reply carries the replier's signed records and the certificates for them whose ids the request did not list. When the opener holds anything the version 2 records cannot carry, an unsigned member, a Left without its signed proof, or when it is joining, it also opens a version 1 exchange (B), the push-pull 0.4 sends, on a second connection. Each connection still carries one frame each way, which is what kinship-net supports. The acceptor answers each as it answers today and keeps no state between them; a version 1 request is answered with its whole table, as for a 0.4 node.
- **Completeness.** B is today's anti-entropy, so every record a 0.4 cluster would exchange is still exchanged by every node that holds one, and A adds the proofs and certificates. A signing node whose own view is all signed sends only A; what its partner holds unsigned reaches it when that partner opens its own exchanges, which it does every `push_pull_interval` with B. A join always runs both, so a joiner learns the 0.4 members at once, as in a 0.4 cluster.
- **Acceptance.** Unsigned statements from version 1 packets are accepted, as the plan's table for `sign` says, and make the member unsigned when they are news. A signed statement is never accepted as unsigned: one whose signature fails, whose certificate fails, or whose certificate this node does not hold and the packet does not carry, is dropped. A signed Alive identical to an unsigned one the node holds, as happens when a 0.4 relay delivered it first, is checked and, when good, attaches its proof. That is news too: without it, the node could not forward the member's signature or count it as signed.

No documented rule is weakened. Rule 3 still holds for signed statements: a node forwards a signature only after checking it. That 0.4 relays strip signatures is the plan's own premise for `sign`.

### 3. Opening a version 1 envelope

The envelope version byte is authenticated, as part of the AEAD associated data, so it binds the choice: a signing node opens with `open_versioned`, which reads a version 1 envelope with the version 1 grammar and a version 2 envelope with the strict version 2 grammar. Since no Stage 2 sender puts version 2 bodies into version 1 envelopes, there is nothing to guess. A version 1 packet carries no proofs by definition: bytes after the known fields of a message are skipped, as 0.4 skips them, and are never read as a signature, so a statement cannot fail a check there and then be taken as unsigned. A node that wants to sign a statement to a signing peer sends it at version 2. `open_v2` is not used by the runtime.

The two grammars cannot be confused in any case. For every message type, version 2 appends fields after the version 1 fields, the epoch becomes mandatory, and the body must end exactly after its signature; version 1 writers add nothing after the epoch. Names, addresses and metadata carry their own lengths, so the version 1 fields parse to the same prefix under both grammars, and a canonical version 1 body is shorter than any version 2 body with the same prefix by at least the 72 bytes of certificate id and signature (Alive, Suspect, Dead, user messages), the 25 bytes of epoch, challenge and flag (Ping), or more (PingReq, Ack, Nack, push-pull records). No version 1 body written by kinship parses as a version 2 body.

### 4. The clock for certificates

As section 2 Clock specifies, the node estimates Unix time as the epoch it started with, which kinship-net takes from the wall clock in milliseconds, plus the time it has been running on the core's monotonic `Instant`, and checks certificates against that in whole seconds. The epoch used is the one in the node's `Identity`, not the one it holds later: moving past a later life of its own name changes the epoch but not the time. A config with an identity on a node whose epoch is 0 is refused, as is one whose own certificate is not valid at that clock. The skew is fixed at 5 minutes on both sides; making it configurable is Stage 4. Cluster time, the replay clock, is not used: it can be moved by any key holder (KI-06).

### 5. Spreading the checks of a large push-pull frame

Precedence comes first (rule 4), so a frame costs a check only for its news. Each input, whatever it is, may spend at most 64 checks on push-pull records, about 5 ms on the laptop of the plan's measurements. When a frame's news goes past that, the records left are copied out of the frame, with its certificates and its admission budget, and handled 64 checks at a time on the inputs that follow; `poll_timeout` asks to be called at once while any are left, so a driver interleaves them with the datagrams and timers it already has. Each deferred record is judged against the node's state when its turn comes. The deferred records are at most `max_members`, beyond which a frame's remaining records are dropped. The reply to a push-pull goes out at once, from the state before its deferred records are applied. A join of 1,000 members, a certificate and an Alive to check for each, spreads its 170 ms over 32 inputs. Batch verification, which would need random coefficients from the nonce key, is not used.

## Design (Stage 2b)

Stage 2b signs the rest of what a member says: its probe answers, its user messages and its broadcasts. Five more questions had to be settled first. Version 1 accusation semantics still hold in both modes, and mode `off` sends the bytes 0.4 sends.

### 6. The challenge source

Each version 2 probe round carries 16 bytes the prober draws from a ChaCha20 keystream keyed with the node's `nonce_key`, the key its packet nonces come from, under a second 8-byte stream IV of its own (`kchallng`, where nonces use zero). The driver already supplies that key from the OS in production and from the run's seed in the simulator, so the core still reads no RNG and every simulator run replays.

- **Unpredictable.** ChaCha20 under a secret 256-bit key is a pseudorandom function of its IV and counter: no number of outputs, from either stream, tells anything about another. Every key holder can read the challenges, since the cluster key opens the Ping that carries them, and every packet shows its nonce, but neither helps to guess the next round's challenge.
- **Independent for each round.** A round draws the next 16 bytes of the stream and nothing else does, so no two rounds share a challenge, and a relay's round is the requester's.
- **Not shared with the nonces.** One stream for both would be as safe, but every challenge drawn would then shift every later nonce, and nonces are what a packet shows on the wire. Two streams keep the nonce sequence a function of the packets sent alone.
- **The protocol RNG is not touched**, so drawing a challenge moves no probe order, gossip target or timer. A node in mode `off` has no challenge stream at all and runs version 1 rounds only: its bytes and the pinned SWIM trace are unchanged.

### 7. Probe versions per round

- **Which rounds are version 2.** A signing node runs a version 2 round with a target that advertises version 2 and whose certificate it holds and finds current: the only targets whose answers it can check. Every other round, to a 0.4 or `off` member or to a member it holds unsigned, is the version 1 round of today, byte for byte. A target held unsigned is no worse off for it: its Alive is unsigned too, until anti-entropy or an announcement brings the proof.
- **The messages.** The round's Ping is a version 2 Ping with the prober's epoch and the challenge. Its PingReqs name the requester, its epoch and the challenge; a version 2 round asks only relays that speak version 2 and whose certificates the prober holds, since only they can answer with a Nack it can check. The relay pings the target with its own sequence number and the requester's challenge, name, epoch and sequence number unchanged, at the address it holds for the target's name, and answers at the address it holds for the requester's, falling back to the addresses in the PingReq only for names it does not hold. A relay that holds the target as Left answers with the target's signed Left, when it kept one, and with the version 1 Left otherwise. The TCP fallback sends the round's own version 2 Ping, the same sequence number and challenge, in a version 2 frame.
- **What answers a round.** A target answers a version 2 Ping with an Ack signed over the original requester's name, epoch and sequence number, the challenge, its own name, epoch and certificate id, whoever sent the Ping. The prober accepts only an Ack for the exact round it is running, its sequence number, its name and epoch, the round's target and an epoch of that target's life, and the round's challenge, signed by that target, by whichever path it came: direct, through a relay or over TCP. A relay correlates the Ack it receives by that whole binding, not by its own sequence number, checks it, and forwards the same message, which version 2 encodes one way only, so the requester gets the target's bytes.
- **Version 1 Acks.** A version 1 Ack does not answer a version 2 round. Mode `sign` takes unsigned statements from members that cannot sign, but a version 2 round goes only to a target that can, and answering it unsigned is exactly the blanket Ack that the challenge closes: a version 1 Ack names a sequence number alone, which anyone can guess. For the same reason a version 1 Nack does not count in a version 2 round. Version 1 rounds take version 1 answers as before.
- **Nacks.** A relay signs its Nack over the round's binding and its own name and epoch. The prober counts it once, if it comes from a relay it asked in this round, at the epoch it holds for that relay, and checks it; a second copy, or a Nack from a relay it did not ask, is dropped unchecked. Missed Nacks still raise local health as in Lifeguard.

### 8. Packets once probes are version 2

To a member that speaks version 2, a datagram whose head, the probe message, is version 2 carries it with the signed rumours, each new Alive behind its certificate, and the signed broadcasts, in one version 2 packet. A version 1 packet goes beside it only for what the version 2 grammar cannot carry: unsigned rumours, which a signing node holds whenever its cluster has a 0.4 or `off` member, and unsigned broadcasts, from 0.4 senders or relayed by 0.4 nodes. In a cluster where every node signs and every member is held signed, that version 1 packet is never sent, so the second datagram of Stage 2a goes. A head that stays version 1 (a version 1 round, a relay's version 1 Ack or Nack, the answer to a version 1 Ping) goes in the version 1 packet, as Stage 2a sends it.

Nothing is lost in mixed clusters. Each queued rumour and broadcast still goes out once per datagram pair, in its version 2 form to members that speak it when it is signed, and in its version 1 form otherwise; members that speak version 1 only get the one version 1 packet, as `off` sends it. Anti-entropy is unchanged from Stage 2a: the version 2 exchange carries the signed records, and the version 1 exchange beside it everything else.

### 9. Signed user messages

- **Direct messages.** A signing node sends a direct message to a member that speaks version 2 in a version 2 packet, signed under the 24-byte nonce of the packet that carries it: the node draws the nonce, signs the message over its body and the nonce, and seals with the same nonce. Its certificate goes ahead of the message, and its signed Alive too while that is still being spread, as the Alive goes ahead of it in version 1, as far as they fit beside it, so that a receiver that has not checked the sender's certificate yet can check the message: it has no second copy to wait for. A message too large for a datagram goes in a version 2 frame, every message in it signed under the frame's nonce, behind the sender's signed Alive and certificate. To other members it goes in version 1, unsigned, as today.
- **Receiving one.** The receiver checks what it checks today first, that the message is for this run of it and from a member it holds at that epoch, then the signature against the nonce of the packet it came in. A packet that holds the same message with the same proof twice, which a key holder can build by resealing an unseen nonce, delivers it once, and the copy costs no check.
- **Broadcasts.** A signing node signs its broadcasts over sender, epoch, sequence number, data and certificate id, and relays them with that signature and the sender's certificate ahead of them. A receiver checks the copy rules first, then the signature, and only then delivers the broadcast, remembers it as seen and queues it to relay, so a broadcast whose check failed is neither delivered nor relayed and a good copy that comes later still counts. The certificate costs about 150 bytes a copy. Without it, a member that had not checked the sender's certificate yet, as happens while a cluster started from static member lists exchanges its announcements, could check no copy and lost it: in the simulator broadcasts then reached 97.5% of the members of all-signing clusters of eight, against 99.4% in 0.4; with it they reach 99.4%. Relaying it only from nodes that had lacked the certificate themselves did not close that gap. A receiver that holds the certificate checks under the one it holds, and the copy ahead costs it nothing.
- **Unsigned messages** from 0.4 senders, or relayed by 0.4 nodes, are still taken in `sign`, as unsigned statements are. A message or broadcast in a version 2 packet is never taken as unsigned: one whose signature or certificate fails, or whose certificate this node does not hold and the packet does not carry, is dropped and counted under `user_messages_dropped`, with `signatures_invalid` or `certificates_refused` when a check failed.

### 10. Precedence first for answers and copies

Rule 4 applies to every new signed message, so each costs at most one check. An Ack is checked only when it matches the exact binding of the round this node runs, and that round has not been answered yet, or of a round it relays and has not forwarded yet. A Nack only when it matches the round, comes from a relay asked in it, and that relay's Nack has not counted yet. A broadcast copy only when it is new by sender, epoch and sequence number, from a sender this node holds at that epoch. A direct message only when it is for this node's run, from a sender it holds, and not a repeat of a proof already in the packet. What fails those cheap tests is dropped unchecked.

## Implementation (Stage 2a)

- **Configuration.** `Config::signatures` is `Signatures::Off`, the default, or `Signatures::Sign(Credentials)` with the node's `signing_key`, its `certificate` (the bytes `Certificate::encode` writes) and the `trust_anchors`. `Config::validate` refuses an identity without encryption, without anchors, with a certificate that does not decode, is for another key, another cluster or no anchor, and limits under which a signed Alive with `max_meta_bytes` of metadata does not fit a datagram behind a certificate for a 64-byte name. `Node::new` refuses epoch 0, a certificate for another name, one that is not valid at the node's clock, and an IPv6 address with a scope or flow label, which version 2 cannot carry. A signing node advertises versions 1 to 2, and its header check takes both.
- **Signing.** The node signs its own Alive whenever it changes (start, `SetMeta`, refutation, moving past a later life of its name), its Left, the Suspect that ends a failed probe round and the Dead that ends a suspicion. Accusations carry the node's cluster time as `at`; Stage 3 checks it.
- **Checking.** `process_v2` and the push-pull merge apply each statement's precedence first and check only news. Alive, Left, Suspect, Dead and push-pull records each have a check-then-apply path; a Suspect or Dead record, the sender's claim, is applied as the merged suspicion it starts once the Alive it carries checks. The counters are `signatures_invalid`, `certificates_refused` and the gauge `unsigned_members`.
- **Announcements.** Found while testing mixed clusters, where a node may learn a member that speaks version 2 only through a version 1 path: a static member list, whose entries carry versions 1 to 1 until an Alive replaces them, or a 0.4 relay or 0.4 push-pull, which passes those entries on as they are. Neither side would then send the other its signature until anti-entropy happened to pair them. So when a node learns that a member speaks version 2, because it is new, starts a new life, or now advertises version 2, it sends that member its own signed Alive, behind its certificate, in one version 2 datagram. It does not when it learned the member from a version 2 push-pull record: the exchange that brought the member also carries this node's own signed record. A signed Alive identical to the one held but for its version range also attaches its proof, and gives the member the range it signed: a 0.4 node passes on a listed member's range as 1 to 1.
- **Tests.** `crates/kinship-core/tests/signatures.rs` covers, for Alive, Left, Suspect, Dead and push-pull records, a good signature, a bad one, a missing one, the wrong signer, and certificates that are expired, not yet valid, for another cluster or from an unknown anchor, plus a certificate that expires while held, a frame with one bad record, the spreading of a large frame's checks, per-recipient versions, seeds at version 2 then version 1, `off` refusing version 2, and the configuration checks. `crates/kinship-sim/tests/signatures.rs` runs the released kinship-core 0.4.0 beside signing nodes, and pins a trace with every node signing. The pinned SWIM trace in `tests/swim.rs` is unchanged.

### Decisions

Accepted by Nikola on 2026-10-18: no upgrade envelope on the wire; the second datagram to members that speak version 2 until Stage 2b moves probes to version 2; the second, version 1 push-pull exchange in mixed views, with digest push-pull as the remedy if Stage 2c finds it too costly; and announcements, capped after Stage 2c measures them.

## Implementation (Stage 2b)

- **Challenges.** `Keys` holds the challenge stream, `Nonces::challenges(nonce_key)`, ChaCha20 under the stream IV `kchallng`; a node in `off` has none. Each version 2 round draws 16 bytes from it when it starts.
- **Rounds.** A round is version 2 when its target advertises version 2 and the node holds a current certificate for it (`probe.rs`); `Probe::signed` keeps its challenge, the node's epoch in the Ping and the relays asked. The Ping goes with the prober's signed Suspect ahead of it when the target is suspected (version 2 has no unsigned Suspect), the PingReqs go only to Alive relays that speak version 2 and whose certificates the node holds, and the TCP fallback sends the same Ping in a version 2 frame. A target answers with `signed_ack`, over UDP and TCP alike. The relay correlates the Ack by the whole binding in `Relay::signed`, checks it and forwards the message unchanged, and signs its Nack when it is due. `on_signed_ack` and `on_signed_nack` apply rule 4, then `check`. The version 1 paths take a version 1 Ack or Nack only for a version 1 round, over UDP and TCP.
- **Packets.** `Outbox::send_split` takes a version 1 head and a version 2 head, and packs the signed rumours and signed broadcasts beside the version 2 one, the unsigned ones beside the version 1 one; a packet goes only when it has something in it. `Node::send_to_v2` sends a version 2 head.
- **User messages.** `Command::Send` to a member that speaks version 2 signs the message over the nonce `Outbox::nonce` draws and seals with it (`send_signed_at`, `frame_v2_at`), with the node's certificate ahead, and its signed Alive while that is being spread; frames carry the Alive and certificate always. `Command::Broadcast` signs the broadcast, which the queue keeps with its signature and the certificate it was checked under, and sends in version 2 to members that speak it. `on_signed_users` handles a version 2 packet's or frame's messages after its statements, dropping repeated proofs, and `on_user_broadcast` checks copy rules, then the signature, then remembers, delivers and queues.
- **Configuration.** In mode `sign`, `Config::validate` also refuses limits under which a signed Alive with `max_meta_bytes` of metadata does not fit beside the largest version 2 probe message (a relay's Ping, a PingReq, an Ack or a Nack, with 64-byte names), a signed `max_user_broadcast` broadcast behind its certificate does not fit beside it, or a signed `max_user_message` message does not fit a frame. At the default `udp_max_payload` a signed broadcast can be at most 688 bytes, against 1,108 unsigned; the default `max_user_broadcast`, 256 bytes, fits either way.
- **Sizes.** With 17-byte names a version 2 Ping is 74 bytes (49 in version 1), a PingReq 81 (39), an Ack 147 (6) and a Nack 165 (6). The plan's sketch counted 57 for the Ping and 78 for the Ack, before Stage 1 added the explicit names, the challenge and the certificate id; Stage 2c remeasures what that costs a node a second.
- **Tests.** `crates/kinship-core/tests/signed_answers.rs`: for Ack, Nack, UserMessage and UserBroadcast, a good signature, a bad one, a missing one (a version 1 Ack or Nack answers no version 2 round; a version 1 message or broadcast is taken), the wrong signer, and the four certificates that must be refused; Acks of another challenge, sequence number or requester epoch dropped unchecked, and copies of an Ack, a Nack or a broadcast already taken unchecked; Nacks counted once per relay asked, never from one not asked; a direct message signed over another nonce refused, and one whose proof repeats three times in a packet delivered once for one check; with real nodes, the Stage 1 harvesting case (an Ack the live target signed for the prober's next sequence number, under another challenge, does not answer that round after the target crashed: the round fails and the target is declared dead), a relay forwarding the target's Acks byte for byte, a relay's forged Acks refused, every TCP fallback Ping carrying its round's sequence number and challenge and answered, version 2 probe packets carrying the signed rumours with no version 1 datagram beside them unless an unsigned rumour waits, signed direct messages in a datagram and in a frame, and the broadcast limit. `crates/kinship-sim/tests/signatures.rs` adds a run of user messages and broadcasts in clusters of eight, three on 0.4.0 and all signing, checked as `tests/usermsg.rs` checks one version: every direct message arrives, none twice, broadcasts reach 99.4% of members as in 0.4, and every signature and certificate check passes. The mixed-cluster detection test passes unchanged.
- **Pinned traces.** The SWIM trace in `tests/swim.rs` is unchanged: mode `off` draws no challenge and sends the bytes 0.4 sends. The pinned trace in `sign` changed, to `0x5a25_2ea5_b273_8cd7`, because its rounds are now version 2: the Pings carry challenges, the Acks are signed, and the signed rumours ride the probe packets instead of a second datagram, which also changes every nonce drawn after the first round.

### Decisions

Accepted by Nikola on 2026-10-23:

1. A version 1 Ack or Nack answers no version 2 round, and version 2 rounds go only to targets held with a current certificate, through relays the prober can check. Targets held unsigned keep version 1 rounds until their proof arrives.
2. A signed broadcast travels behind its sender's certificate in every version 2 packet, about 150 bytes a copy, so that it reaches the members of clusters started from static lists as surely as in 0.4; a signed direct message carries the certificate too when it fits. Stage 2c measures the cost, and an exchange of certificates when a node first speaks to a member could replace it.
3. The announcement cap of Stage 2a was not measured here, and stays for Stage 2c.

## Implementation (Stage 2c)

Stage 2c measures mode `sign` and fixes what the measurements found. The numbers are in [results/signed.md](results/signed.md).

- **Sweeps.** Each 1,000-seed sweep of `tests/swim.rs`, `sync.rs`, `epoch.rs`, `usermsg.rs`, `failure.rs` and `keyring.rs` has a twin, named with `_signed`, that runs the same seeds with every node of this version in `sign`, under certificates from one CA, each life with a key of its own (`common::Mode`). Every signing node must also end with no signature or certificate refused. Nodes without an epoch cannot sign: the restart without epochs has no twin, and the older nodes of the mixed-version sweep stay in `off`. All of them pass.
- **Three bugs the sweeps found, fixed.** A relay checks the target's Ack before it forwards it, and the prober picks relays it can check, not relays that hold the target's certificate, so indirect probes through a relay that lacked it failed and suspected live members: an Ack to a relay's Ping now goes behind the target's certificate. A later life of a member heard of unsigned kept the earlier life's certificate, and its rounds were version 2 rounds it could never answer under the new key: the certificate goes with the earlier life, and the rounds stay version 1 until the new life's proof arrives. A member back from the dead was relayed without its certificate, and nodes that had reaped its tombstone could not check it: an Alive that revives a member goes behind the certificate, as one that is new does. Each has a test in `crates/kinship-core/tests/signed_answers.rs`.
- **Certificate gaps.** A node started from a static member list holds its members without their certificates until an Alive brings them, and drops their signed statements meanwhile: Deads, refutations, metadata. In the epoch sweep a node that lacked the accusers' certificates so declared a crashed member dead only after its own suspicion ran out, by when the others had reaped the tombstone (seed 499). A member that speaks version 2 and still probes this node in version 1 is one that holds it without a current certificate, so a version 1 Ping from such a member is answered with an announcement as well as the Ack, and the gap closes within a probe pass.
- **Announcement cap.** A join that learns the cluster through its version 1 exchange learns every member at once, and a node sent an announcement to each in the same instant: 896 datagrams from one node in a 1,000-node cluster. A node now sends at most four announcements per gossip interval (`ANNOUNCEMENTS_PER_TICK`), and queues the rest, one per member, for the intervals that follow, sending each if the member still speaks version 2 then. The cap does not change what a joiner receives from the members that learn of it, one announcement each.
- **Counters.** `Metrics::signatures_made` and `signatures_checked` count the statements a node signs and the Ed25519 signatures it verifies, certificates' included, for the cost per node.
- **Tuning and costs.** `tests/tuning.rs` has a `signed` stage: `lan()` in `sign` against `lan()` in `off`, both with epochs, on the screen's cells and seeds, compared by `signed_verdict`. `tests/costs.rs` opens every packet the plan's clusters send and files each message under its carrier.
- **CI.** The sweeps in mode `sign` are about ten times slower than in `off` and do not fit the existing jobs: those skip them (`--skip _signed`), and a `sim-signed` job runs them, one job per file, at 250 seeds.
- **Pinned traces.** The SWIM trace in `off` is unchanged. The trace in `sign` changed, to `0xd425_7421_477d_9eeb`: Acks to relays' Pings carry the target's certificate, version 1 Pings between signing nodes draw announcements, and announcements go four per gossip interval.

### What remains

- Stage 3: mode `require`, third-party Deads as confirmations with the K + 1 shortcut, `at` checked against the replay floor, and dropping the rest of a packet at its first bad signature.
- Stage 4: revocation, renewal and the choice between two certificates by `not_before`, configurable skew, the budget of failed checks and the per-signer limits.
- Stage 5: kinship-net, the facade, Python and the CLI. kinship-net passes `Config::signatures` to the core as it passes every core field, so a Rust program on kinship-net can already try mode `sign`, untested there; the facade, the Python package, `stats()` in Python and the CLI expose none of it.
