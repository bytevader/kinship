# Stage 2 implementation notes

Stage 2 of [the per-member keys plan](ki01-per-member-keys.md) puts identities into kinship-core. It is split in three: Stage 2a (this note) adds the identity configuration, mode `sign` for statements about membership, certificate distribution, per-recipient wire versions and the new counters; Stage 2b adds the Ack and Nack bindings, the probe challenge and signed user messages and broadcasts; Stage 2c runs the 1,000-seed sweeps in `sign`, the signed tuning comparison and remeasures the costs. Nothing here changes a node in mode `off`, the default: it sends the bytes 0.4 sends and the pinned SWIM trace is unchanged. KI-01 stays Accepted, and the feature stays opt-in and planned for a release after 1.0.

## Design

Five questions had to be settled before the code. Each answer keeps version 1 accusation semantics in both modes: a third party's Dead still kills at once, in `sign` as in `off`, until Stage 3.

### 1. Where signatures and certificates live

- **The member table** keeps, beside each member, the proof of the Alive it holds: the incarnation that Alive was signed at, its certificate id and its signature. The rest of the signed bytes (name, address, metadata, version range and epoch) are the member's own fields, which only an Alive replaces, and every path that replaces them sets the proof again or clears it. A member suspected at a higher incarnation keeps the proof of its last Alive, which is what a version 2 push-pull record carries as its original Alive (Stage 1, Push-pull). A Left keeps the member's signed Left beside it (`left` incarnation, `at`, certificate id, signature). A member without a proof for its current Alive is unsigned; `unsigned_members` counts the live ones.
- **Certificates** are held one per member, in a map by name, as the parsed key and validity with the exact bytes they arrived in. A member's certificate is the one its applied Alive was signed under, so it follows the member through a restart with a new key; choosing between two valid certificates by `not_before` is renewal, which is Stage 4. A certificate goes when its member's tombstone is reaped. This node's own certificate is held the same way.
- **The gossip queue** keeps the proof with each rumour: the Alive's certificate id and signature, or an accusation's `at`, certificate id and signature, and for an Alive that is new to the node gossiping it, the certificate's bytes, so it goes ahead of the Alive in every packet that carries it. Each entry knows its length in both grammars.
- Relays and push-pull rebuild the signed messages from these fields. The version 2 encoding has one encoding per value, so the rebuilt bytes are the bytes the author signed, and a relay forwards the signature unchanged.

### 2. Unsigned statements in `sign`

The version 2 grammar has no unsigned Alive, Suspect, Dead or push-pull record, and a signing node holds unsigned ones whenever its cluster has a 0.4 or `off` node: their own Alives, and whatever they relayed, since a 0.4 node drops what it does not know.

- **Envelope selects grammar.** A version 2 packet holds version 2 messages only, all of them signed membership statements, certificates or push-pull; a version 1 packet holds the version 1 grammar, exactly as 0.4 writes it. A signing node never writes a version 2 body into a version 1 envelope, so the upgrade envelope of Stage 1 is not used on the wire.
- **Datagrams to a member that speaks version 2** go out as up to two packets: a version 1 packet with the probe messages (Ping, PingReq, Ack, Nack, which stay version 1 until Stage 2b), the unsigned rumours and the user broadcasts, and a version 2 packet with the signed rumours, each new Alive behind its certificate. Each packet takes its rumours in queue order from the room it has; a rumour goes once per datagram pair and counts one transmission. A member that speaks version 1 only gets the one version 1 packet, every rumour in it in its version 1 form, as `off` sends it.
- **Push-pull with such a member** is a version 2 exchange (A): the signed records, the sender's own certificate, and the ids of the certificates it holds; the reply carries the replier's signed records and the certificates for them whose ids the request did not list. When the opener holds anything the version 2 records cannot carry, an unsigned member, a Left without its signed proof, or when it is joining, it also opens a version 1 exchange (B), the push-pull 0.4 sends, on a second connection. Each connection still carries one frame each way, which is what kinship-net supports. The acceptor answers each as it answers today and keeps no state between them; a version 1 request is answered with its whole table, as for a 0.4 node.
- **Completeness.** B is today's anti-entropy, so every record a 0.4 cluster would exchange is still exchanged by every node that holds one, and A adds the proofs and certificates. A signing node whose own view is all signed sends only A; what its partner holds unsigned reaches it when that partner opens its own exchanges, which it does every `push_pull_interval` with B. A join always runs both, so a joiner learns the 0.4 members at once, as in a 0.4 cluster.
- **Acceptance.** Unsigned statements from version 1 packets are accepted, as the plan's table for `sign` says, and make the member unsigned when they are news. A signed statement is never accepted as unsigned: one whose signature fails, whose certificate fails, or whose certificate this node does not hold and the packet does not carry, is dropped. A signed Alive identical to an unsigned one the node holds, as happens when a 0.4 relay delivered it first, is checked and, when good, attaches its proof. That is news too: without it, the node could not forward the member's signature or count it as signed.

No documented rule is weakened. Rule 3 still holds for signed statements: a node forwards a signature only after checking it. That 0.4 relays strip signatures is the plan's own premise for `sign`.

### 3. Opening a version 1 envelope

The envelope version byte is authenticated, as part of the AEAD associated data, so it binds the choice: a signing node opens with `open_versioned`, which reads a version 1 envelope with the version 1 grammar and a version 2 envelope with the strict version 2 grammar. Since no Stage 2 sender puts version 2 bodies into version 1 envelopes, there is nothing to guess. A version 1 packet carries no proofs by definition: bytes after the known fields of a message are skipped, as 0.4 skips them, and are never read as a signature, so a statement cannot fail a check there and then be taken as unsigned. A node that wants to sign a statement to a signing peer sends it at version 2. `open_v2` is not used by the runtime.

The two grammars cannot be confused in any case. For every message type, version 2 appends fields after the version 1 fields, the epoch becomes mandatory, and the body must end exactly after its signature; version 1 writers add nothing after the epoch. Names, addresses and metadata carry their own lengths, so the version 1 fields parse to the same prefix under both grammars, and a canonical version 1 body is shorter than any version 2 body with the same prefix by at least the 72 bytes of certificate id and signature (Alive, Suspect, Dead, user messages), the 25 bytes of epoch, challenge and flag (Ping), or more (PingReq, Ack, Nack, push-pull records). No version 1 body written by kinship parses as a version 2 body.

### 4. The clock for certificates

As section 2 Clock specifies, the node estimates Unix time as the epoch it started with, which kinship-net takes from the wall clock in milliseconds, plus the time it has been running on the core's monotonic `Instant`, and checks certificates against that in whole seconds. The epoch used is the one in the node's `Identity`, not the one it holds later: moving past a later life of its own name changes the epoch but not the time. A config with an identity on a node whose epoch is 0 is refused, as is one whose own certificate is not valid at that clock. The skew is fixed at 5 minutes on both sides; making it configurable is Stage 4. Cluster time, the replay clock, is not used: it can be moved by any key holder (KI-06).

### 5. Spreading the checks of a large push-pull frame

Precedence comes first (rule 4), so a frame costs a check only for its news. Each input, whatever it is, may spend at most 64 checks on push-pull records, about 5 ms on the laptop of the plan's measurements. When a frame's news goes past that, the records left are copied out of the frame, with its certificates and its admission budget, and handled 64 checks at a time on the inputs that follow; `poll_timeout` asks to be called at once while any are left, so a driver interleaves them with the datagrams and timers it already has. Each deferred record is judged against the node's state when its turn comes. The deferred records are at most `max_members`, beyond which a frame's remaining records are dropped. The reply to a push-pull goes out at once, from the state before its deferred records are applied. A join of 1,000 members, a certificate and an Alive to check for each, spreads its 170 ms over 32 inputs. Batch verification, which would need random coefficients from the nonce key, is not used.

## Implementation (Stage 2a)

- **Configuration.** `Config::signatures` is `Signatures::Off`, the default, or `Signatures::Sign(Credentials)` with the node's `signing_key`, its `certificate` (the bytes `Certificate::encode` writes) and the `trust_anchors`. `Config::validate` refuses an identity without encryption, without anchors, with a certificate that does not decode, is for another key, another cluster or no anchor, and limits under which a signed Alive with `max_meta_bytes` of metadata does not fit a datagram behind a certificate for a 64-byte name. `Node::new` refuses epoch 0, a certificate for another name, one that is not valid at the node's clock, and an IPv6 address with a scope or flow label, which version 2 cannot carry. A signing node advertises versions 1 to 2, and its header check takes both.
- **Signing.** The node signs its own Alive whenever it changes (start, `SetMeta`, refutation, moving past a later life of its name), its Left, the Suspect that ends a failed probe round and the Dead that ends a suspicion. Accusations carry the node's cluster time as `at`; Stage 3 checks it.
- **Checking.** `process_v2` and the push-pull merge apply each statement's precedence first and check only news. Alive, Left, Suspect, Dead and push-pull records each have a check-then-apply path; a Suspect or Dead record, the sender's claim, is applied as the merged suspicion it starts once the Alive it carries checks. The counters are `signatures_invalid`, `certificates_refused` and the gauge `unsigned_members`.
- **Announcements.** Found while testing mixed clusters, where a node may learn a member that speaks version 2 only through a version 1 path: a static member list, whose entries carry versions 1 to 1 until an Alive replaces them, or a 0.4 relay or 0.4 push-pull, which passes those entries on as they are. Neither side would then send the other its signature until anti-entropy happened to pair them. So when a node learns that a member speaks version 2, because it is new, starts a new life, or now advertises version 2, it sends that member its own signed Alive, behind its certificate, in one version 2 datagram. It does not when it learned the member from a version 2 push-pull record: the exchange that brought the member also carries this node's own signed record. A signed Alive identical to the one held but for its version range also attaches its proof, and gives the member the range it signed: a 0.4 node passes on a listed member's range as 1 to 1.
- **Tests.** `crates/kinship-core/tests/signatures.rs` covers, for Alive, Left, Suspect, Dead and push-pull records, a good signature, a bad one, a missing one, the wrong signer, and certificates that are expired, not yet valid, for another cluster or from an unknown anchor, plus a certificate that expires while held, a frame with one bad record, the spreading of a large frame's checks, per-recipient versions, seeds at version 2 then version 1, `off` refusing version 2, and the configuration checks. `crates/kinship-sim/tests/signatures.rs` runs the released kinship-core 0.4.0 beside signing nodes, and pins a trace with every node signing. The pinned SWIM trace in `tests/swim.rs` is unchanged.

### What remains

- Stage 2b: Ack and Nack bindings and the probe challenge, which move probes to version 2; signed user messages and broadcasts.
- Stage 2c: the 1,000-seed sweeps in `sign`, the signed tuning comparison at 50, 200 and 1,000 nodes, and the remeasured costs, including the second datagram to members that speak version 2, the second push-pull exchange in mixed views and the announcements, which a join into a large signing cluster receives from every member that learns it from gossip.
- Stage 3: mode `require`, third-party Deads as confirmations with the K + 1 shortcut, `at` checked against the replay floor, and dropping the rest of a packet at its first bad signature.
- Stage 4: revocation, renewal and the choice between two certificates by `not_before`, configurable skew, the budget of failed checks and the per-signer limits.
- Stage 5: kinship-net, the facade, Python and the CLI. kinship-net passes `Config::signatures` to the core as it passes every core field, so a Rust program on kinship-net can already try mode `sign`, untested there; the facade, the Python package, `stats()` in Python and the CLI expose none of it.
